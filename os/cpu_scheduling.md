## CPU 스케줄링

> `process_thread.md`에서 "쓰레드는 CPU 입장에서 최소 작업 단위"라고 정리했었는데, 그 여러 개의 쓰레드/프로세스 중 **CPU가 다음에 누구를 실행시킬지 결정하는 규칙**이 CPU 스케줄링이다.

## 왜 필요한가

- CPU 코어 수는 한정되어 있는데(예: 8코어), 실행 대기 중인 프로세스/쓰레드는 수백 개일 수 있음.
- 운영체제는 아주 짧은 시간 단위로 실행 주체를 바꿔가며(문맥 교환, Context Switch) 동시에 여러 작업이 진행되는 것처럼 보이게 만든다 — 이게 멀티태스킹의 실체.
- 스케줄링 알고리즘이 "누구를, 얼마나, 어떤 순서로" 실행시킬지 결정.

## 스케줄링 평가 기준

| 기준 | 의미 |
|---|---|
| 처리율(Throughput) | 단위 시간당 완료되는 프로세스 수 |
| turnaround time | 프로세스가 실행 요청된 시점부터 완료까지 걸린 전체 시간 |
| 대기 시간(Waiting Time) | 준비 큐(ready queue)에서 대기한 시간의 합 |
| 응답 시간(Response Time) | 요청 후 첫 반응이 나오기까지 걸린 시간 (turnaround와 다름 — 인터랙티브한 시스템일수록 중요) |

- 대부분의 스케줄링 알고리즘은 이 기준들 사이에서 트레이드오프를 가진다 (처리율을 올리면 특정 프로세스의 대기시간이 길어지는 식).

## 대표 알고리즘

### FCFS (First-Come First-Served)
- 도착한 순서대로 실행. 구현이 제일 간단하지만, 실행 시간이 긴 프로세스가 먼저 오면 뒤에 있는 짧은 작업들이 한없이 기다려야 함 (Convoy Effect, 호위 효과).

### SJF (Shortest Job First)
- 실행 시간이 짧은 프로세스부터 실행. 평균 대기시간을 이론적으로 최소화할 수 있는 알고리즘.
- 문제: 미래의 실행 시간을 미리 알아야 함(현실적으로 불가능 → 과거 실행 시간 기반으로 추정치를 씀). 실행 시간이 긴 프로세스는 계속 뒤로 밀릴 수 있음(기아, Starvation).

### 우선순위 스케줄링 (Priority Scheduling)
- 우선순위가 높은 프로세스부터 실행. 마찬가지로 낮은 우선순위 프로세스가 영원히 실행되지 못하는 기아 문제가 생길 수 있음.
- 해결책: **에이징(Aging)** — 오래 기다린 프로세스의 우선순위를 시간이 지날수록 점점 높여줘서 언젠가는 실행되도록 보장.

### 라운드 로빈 (Round Robin)
- 각 프로세스에게 정해진 시간 조각(time quantum/time slice, 보통 수~수십 ms)만큼만 CPU를 주고, 시간이 다 되면 강제로 다음 프로세스로 넘어감 (선점형, Preemptive).
- 현대 범용 OS(인터랙티브 시스템)의 기본 골격. quantum이 너무 크면 사실상 FCFS와 비슷해지고, 너무 작으면 문맥 교환 오버헤드가 커져서 오히려 처리율이 떨어짐 — 적절한 값 튜닝이 중요.

### 다단계 큐 / 다단계 피드백 큐 (Multilevel Feedback Queue)
- 우선순위별로 여러 개의 큐를 두고, 프로세스가 CPU를 오래 쓰면(CPU-bound로 보이면) 우선순위가 낮은 큐로, I/O를 자주 기다리면(I/O-bound로 보이면) 우선순위가 높은 큐로 옮겨가며 조정.
- "CPU를 많이 쓰는 배치성 작업"과 "빠른 응답이 중요한 인터랙티브 작업"을 실행 패턴을 관찰해서 자동으로 구분해준다는 것이 핵심 아이디어.

## 리눅스의 실제 스케줄러 — CFS (Completely Fair Scheduler)

- 리눅스 커널(2.6.23 이후)이 기본으로 쓰는 스케줄러. 위에서 다룬 고전 알고리즘들을 그대로 쓰지 않고, **모든 프로세스에게 CPU 시간을 최대한 "공평하게" 나눠주는 것**을 목표로 한다.
- 각 프로세스가 "이미 얼마나 CPU를 썼는지(vruntime, virtual runtime)"를 레드-블랙 트리로 관리하다가, 가장 적게 쓴(vruntime이 가장 작은) 프로세스를 다음에 실행시킨다.
- `nice` 값(우선순위, -20~19)으로 프로세스마다 vruntime이 증가하는 속도(가중치)를 다르게 줘서, 결과적으로 CPU를 더 많이/적게 배분받도록 조정 가능.
    ~~~
    nice -n -5 java -jar app.jar   # 우선순위를 높여서(값은 낮게) CPU를 더 배분받도록
    ~~~

## 애플리케이션 개발자가 이걸 알아야 하는 이유

- 컨테이너/쿠버네티스의 CPU `limits`/`requests`도 결국 이 스케줄링 위에서 동작한다 — `limits`를 걸면 커널이 해당 cgroup의 프로세스에게 특정 시간 이상 CPU를 안 주도록 스로틀링(throttling)하는 것.
- `java_concurrency_executor.md`에서 다룬 쓰레드풀 크기를 "CPU 코어 수"에 맞춰 잡으라는 흔한 조언도, 결국 OS 스케줄러가 코어 수보다 훨씬 많은 쓰레드를 문맥 교환하며 돌리면 그 오버헤드 자체가 성능 손해가 되기 때문.
