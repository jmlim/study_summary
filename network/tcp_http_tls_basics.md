# 네트워크 기초 - TCP, HTTP, TLS

> nginx 로드밸런싱 노트에서 "HTTPS 종료(TLS Termination)"를 설정으로만 다뤘는데, 여기서는 그 아래에 있는 TCP/HTTP/TLS의 동작 원리 자체를 정리.
> 백엔드 개발자 인터뷰에서 단골로 나오는 주제이기도 함.

## 1. TCP - 신뢰성 있는 연결

### 3-way handshake (연결 수립)

~~~
클라이언트                     서버
    |------ SYN (연결 요청) ----->|
    |<--- SYN-ACK (승인+요청) ----|
    |------ ACK (승인) ---------->|
   (연결 완료, 이제부터 데이터 전송 가능)
~~~

- **SYN**: 클라이언트가 "연결하고 싶다"는 신호(시퀀스 번호 포함)를 보냄.
- **SYN-ACK**: 서버가 "받았고, 나도 연결할게"라고 응답(자신의 시퀀스 번호 + 클라이언트 시퀀스 번호+1로 응답).
- **ACK**: 클라이언트가 최종 확인 응답 → 이 시점부터 양방향 통신 가능.
- 왜 2-way가 아니라 3-way인가? 서버가 SYN-ACK을 보냈다는 것만으로는, 그게 클라이언트에게 도착했는지 서버는 알 수 없다. 마지막 ACK까지 받아야 "서로가 서로의 상태를 확인한" 상태가 되어 신뢰성 있는 연결이 성립한다.

### 4-way handshake (연결 종료)

~~~
클라이언트                     서버
    |------ FIN --------------->|   (나 이제 안 보낼게)
    |<----- ACK ----------------|   (알겠어, 근데 나는 아직 보낼 데이터 있어)
    |<----- FIN ----------------|   (나도 이제 다 보냈어)
    |------ ACK --------------->|   (알겠어, 종료)
   (TIME_WAIT 상태로 잠시 대기 후 완전 종료)
~~~

- 연결 종료는 4단계인 이유: TCP는 전이중(full-duplex, 양방향 동시 통신)이라 "나는 그만 보낼게"와 "너도 그만 보낼게"가 독립적으로 이루어져야 하기 때문.
- `TIME_WAIT` — 클라이언트가 마지막 ACK을 보낸 뒤에도 일정 시간 소켓을 바로 재사용하지 않고 대기하는 상태. 지연되어 도착하는 패킷이 새 연결과 섞이는 걸 방지하기 위함.
    - 실무 이슈: 짧은 커넥션을 대량으로 맺고 끊는 서버(로드밸런서 등)에서 `TIME_WAIT` 소켓이 쌓여 포트가 고갈되는 문제가 실제로 발생할 수 있음 — `SO_REUSEADDR`, 커넥션 풀링(keep-alive)으로 완화.

### TCP vs UDP
- TCP: 순서 보장, 재전송, 흐름/혼잡 제어 → 신뢰성은 높지만 오버헤드가 있음. HTTP, DB 커넥션 등 대부분의 애플리케이션 프로토콜의 기반.
- UDP: 순서/재전송 보장 없음, 오버헤드가 적고 빠름. 스트리밍, DNS 조회, 실시간 게임/화상통화(HTTP/3의 기반인 QUIC도 UDP 위에서 동작)에 사용.

## 2. HTTP - 애플리케이션 레벨 프로토콜

### HTTP/1.1의 한계
- 하나의 TCP 연결 위에서 요청-응답이 **순차적**으로 처리됨(Head-of-Line Blocking) — 앞 요청의 응답이 안 끝나면 뒷 요청을 처리 못 함.
    - 브라우저가 도메인당 동시 연결 수(보통 6개)를 늘려서 우회하지만, 그만큼 서버 자원과 TCP 핸드셰이크 비용이 늘어남.
- 매 요청마다 중복되는 헤더(User-Agent, Cookie 등)를 압축 없이 그대로 전송.

### HTTP/2 — 위 문제를 해결
- **멀티플렉싱(Multiplexing)**: 하나의 TCP 연결 위에서 여러 요청/응답을 스트림(stream) 단위로 동시에 주고받음 — Head-of-Line Blocking을 애플리케이션 레벨에서는 해소.
- **헤더 압축(HPACK)**: 반복되는 헤더 정보를 압축해서 전송량 감소.
- **서버 푸시**: 클라이언트가 요청하기 전에 서버가 필요할 것으로 예상되는 리소스를 미리 보내줄 수 있음(실무에서는 캐시 정책과 얽혀 잘 안 쓰이는 추세).
- 단, HTTP/2도 TCP 위에서 동작하기 때문에, TCP 레벨의 패킷 손실이 발생하면 그 연결의 모든 스트림이 영향을 받는 한계(TCP 레벨 HOL Blocking)는 남아있음 → 이 문제를 UDP 기반 QUIC으로 해결한 것이 HTTP/3.

### 상태 코드 감(자주 헷갈리는 것들)
- `301` vs `302` — 영구 이동 vs 임시 이동 (블로그의 `spring-redirect-to-an-external-url.md`에서 다룬 redirect 코드들의 배경)
- `401` (Unauthorized, 인증 안 됨) vs `403` (Forbidden, 인증은 됐지만 권한 없음) — 실무에서 자주 헷갈리는 대표적인 쌍
- `502` (Bad Gateway) — 로드밸런서/게이트웨이가 뒤에 있는 WAS로부터 잘못된 응답을 받음. 앞서 다룬 nginx `upstream` 서버가 죽어있을 때 흔히 나는 에러

## 3. TLS - 암호화된 통신

### TLS Handshake 흐름 (단순화)

~~~
클라이언트                                서버
    |-- ClientHello (지원 암호화 방식 목록) ->|
    |<- ServerHello + 인증서 + 공개키 --------|
    | (인증서 검증: CA가 서명했는지 확인)      |
    |-- 대칭키 재료를 서버 공개키로 암호화 --->|
    |<---- 대칭키로 암호화된 통신 시작 ------->|
~~~

- **비대칭키(공개키/개인키) 암호화**로 처음에 "대칭키를 안전하게 교환"하고, 그 이후의 실제 데이터 통신은 훨씬 빠른 **대칭키 암호화**로 처리한다 — 비대칭키 연산이 무겁기 때문에, 매 패킷마다 쓰기엔 비효율적이라 이렇게 역할을 나눈 것.
    - 블로그의 `java-aes256.md`에서 다룬 AES가 바로 이 "대칭키 암호화" 알고리즘의 하나.
- 인증서(Certificate)는 "이 공개키가 진짜 example.com의 것"임을 CA(인증기관)가 보증하는 역할. 브라우저는 미리 신뢰하는 CA 목록을 갖고 있어서 이 서명을 검증할 수 있다.
- TLS 1.3에서는 핸드셰이크 왕복 횟수를 줄여(1-RTT, 조건부로 0-RTT까지) 접속 초기 지연을 줄였다.

### 이게 nginx 설정과 어떻게 연결되는가
- nginx 로드밸런싱 노트의 "HTTPS 종료" 구조에서, TLS 핸드셰이크(계산 비용이 큰 비대칭키 연산 포함)를 nginx 한 곳에서만 처리하고 내부 WAS와는 평문 HTTP로 통신하는 이유가 바로 이 비용 때문 — 여러 WAS 각각이 TLS 핸드셰이크를 반복하게 하지 않고 한 곳에 집중시켜 자원을 아낀다.
