>  출처 : 디자인패턴의 아름다움 (SOLID) + 일반적으로 통용되는 고전 설계 원칙 정리 (KISS/YAGNI/DRY/LoD)

- SOLID, KISS, YAGNI, DRY, LoD 와 같은 고전적인 설계 원칙 몇가지 소개
- 설계 원칙에 대해 **이해**하는것도 중요하지만, 그보다는 실제 프로젝트에서 사용하는 방법을 정확하게 알고 있어야 함.

## SOLID 원칙 (각 원칙 상세는 개별 문서 참고)

| 원칙 | 한 줄 요약 | 문서 |
|---|---|---|
| SRP (단일 책임) | 클래스/모듈은 하나의 책임만 가져야 한다 | [SRP.md](./SRP.md) |
| OCP (개방-폐쇄) | 확장에는 열려있고, 수정에는 닫혀있어야 한다 | [OCP.md](./OCP.md) |
| LSP (리스코프 치환) | 하위 타입은 상위 타입을 대체해도 프로그램이 깨지면 안 된다 | [LSP.md](./LSP.md) |
| ISP (인터페이스 분리) | 클라이언트는 쓰지 않는 인터페이스에 의존하도록 강요받으면 안 된다 | [ISP.md](./ISP.md) |
| DIP (의존 역전) | 상위 모듈은 하위 모듈이 아니라 추상화에 의존해야 한다 | [DIP.md](./DIP.md) |

SOLID는 전부 "변화에 강한 코드를 만들기 위한 원칙"이라는 공통 목표를 갖는다. 다만 SOLID만으로는 부족하다 — 아래 네 가지는 SOLID보다 훨씬 단순하지만, 실무에서는 오히려 더 자주 어기게 되는 원칙들이다.

## KISS (Keep It Simple, Stupid)

- 불필요하게 복잡한 설계보다는 단순한 설계가 낫다는 원칙.
- 코드가 복잡해지는 원인은 대부분 두 가지다.
    1. 문제 자체가 복잡한 경우 (어쩔 수 없이 복잡해짐)
    2. 개발자가 "있어 보이는" 설계, 과도한 추상화, 미리 예측한 확장성을 코드에 미리 다 집어넣는 경우
- KISS를 지키기 위한 실전 기준
    - 코드가 흔한 프로그래밍 언어/알고리즘/자료구조로 구현되어 있는가?
    - 코드가 개발자의 상식(직관)에 부합하는가?
    - 코드에 놀랄만한(surprise) 요소가 없는가? (한 함수가 이름과 다른 일을 하는 등)
    - 코드가 충분히 짧은가? (짧다고 항상 단순한 건 아니지만, 상관관계는 있음)
- 안티패턴: "혹시 몰라서" 만드는 과도한 추상 클래스/인터페이스 계층, 안 쓰는 설정 옵션, 정규표현식 하나로 모든 걸 처리하려는 시도.
    - `if (isValidIp(ipAddress))` 처럼 이름이 명확한 유틸 함수를 쓰는 게, 정규식을 인라인으로 박아넣는 것보다 KISS에 맞는다.

## YAGNI (You Aren't Gonna Need It)

- "지금 필요하지 않은 기능은 만들지 마라." XP(익스트림 프로그래밍)에서 나온 원칙.
- KISS와 목표는 비슷하지만 관점이 다르다.
    - KISS는 "어떻게 구현할 것인가"에 대한 원칙 (설계를 단순하게).
    - YAGNI는 "무엇을 구현할 것인가"에 대한 원칙 (기능 자체를 만들지 말지).
- 실무에서 YAGNI를 어기는 전형적인 케이스
    - "나중에 다른 DB로 바꿀 수도 있으니" 지금 당장 안 쓰는 추상화 레이어를 미리 만들어둠.
    - "혹시 몰라서" 설정값으로 빼놓은 옵션이 실제로는 한 번도 바뀐 적이 없음.
    - 요구사항에 없는 필드/API를 "확장성을 위해" 미리 추가.
- 다만 YAGNI ≠ "설계를 아예 하지 마라"는 뜻이 아님.
    - 코드 자체는 확장하기 쉽게(OCP를 지키게) 짜되, 그 확장 포인트에 실제 기능을 미리 채워넣지는 말라는 것.
    - 즉 "확장 가능한 구조"와 "당장 필요 없는 기능 구현"은 별개의 문제.

## DRY (Don't Repeat Yourself)

- "코드 중복을 피하라"로 흔히 번역되지만, 원래 정의는 코드 중복보다 훨씬 넓다.
    - "시스템 내의 모든 지식(knowledge)은 단 하나의, 모호하지 않은, 권위있는 표현을 가져야 한다."
- 코드가 똑같이 생겼다고 항상 DRY 위반은 아니고, 반대로 코드가 다르게 생겼어도 DRY 위반일 수 있음.
    - **논리적 중복 (진짜 위반)**: 두 코드가 겉모습은 다르지만 같은 지식/규칙을 표현하고 있다면, 그 규칙이 바뀔 때 두 군데를 다 고쳐야 함 → 위반.
    - **우연한 중복 (위반 아님)**: 두 코드가 지금은 똑같이 생겼지만, 서로 다른 이유로 존재하고 앞으로 독립적으로 바뀔 것이라면 → 억지로 하나로 합치면 오히려 결합도가 올라감.
    - 예) 사용자 나이 검증 로직(0~150)과 상품 재고 수량 검증 로직(0~150)이 우연히 같은 범위를 쓴다고 해서 같은 유틸 메서드로 합치면 안 됨 — 둘은 전혀 다른 도메인 지식.
- 코드 재사용성을 높이는 실전 방법: 코드 블록 추출(함수화), 클래스 병합, 상속/다형성, 템플릿, 라이브러리로 분리, 오픈소스 활용 등.

## LoD (디미터 법칙, Law of Demeter)

- "낯선 사람에게 말하지 마라(Don't talk to strangers)" 라고도 불림.
- 정의: 각 유닛(클래스/모듈/함수)은 자신과 직접 관련된 유닛에 대해서만 알아야 하고, 협력하는 유닛의 내부 구조는 몰라야 한다.
- SRP보다 낮은 응집도가 아니라 "결합도"에 초점을 맞춘 원칙. 좁은 범위의 지식(인터페이스)만 공개하고, 서로 관련 없는 클래스 간에는 상호작용을 최소화한다.
- 실무에서 흔히 보는 위반: 기차 충돌(Train Wreck) 코드
    ~~~java
    // LoD 위반 - a의 내부 구조(b, c)까지 알아야 호출 가능
    a.getB().getC().doSomething();
    ~~~
    - `a`를 사용하는 코드가 `a`뿐 아니라 `a`가 가진 `B`, `B`가 가진 `C`의 존재까지 다 알아야 함 → `B`나 `C`의 내부 구조가 바뀌면 `a`를 쓰는 모든 코드가 영향을 받음.
    - 개선: `a`에 `doSomethingOnC()` 같은 위임(delegate) 메서드를 만들어서, 호출부는 `a.doSomethingOnC()`만 알면 되도록 만든다.
- 단, LoD를 기계적으로 지키겠다고 모든 곳에 위임 메서드를 추가하면 클래스가 비대해짐(SRP 위반) — 원칙끼리 종종 트레이드오프 관계에 있다는 걸 인지하고 균형을 잡아야 함.
